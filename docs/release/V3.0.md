# TKAI V3.0 Enterprise Release

Release date: 2026-07-26

Package version: `3.0.0`

Tag: `v3.0.0`

## Release status

Release candidate validation is complete only when every applicable gate in
this document and `docs/ReleaseChecklist.md` has passed in the target release
environment. Checks unavailable locally must remain explicitly outstanding.

## Architecture

V3.0 keeps a layered, dependency-directed architecture. `tkai` contains the
runtime and SDK; `server` exposes optional HTTP and persistence adapters;
`studio` consumes public SDK and server boundaries; `enterprise`, `cloud`, and
`marketplace` remain independently importable capability packages. Deployment
assets depend on these application contracts, never the reverse. Optional
services and integrations are initialized explicitly.

## Modules

- `tkai`: CLI, configuration, project generation, AI/provider runtime,
  workflows, resilience, telemetry, and public SDK contracts.
- `server`: API, authentication, health, registry, package, release, search,
  statistics, and PostgreSQL persistence adapters.
- `enterprise`: identity, organization, tenants, authorization, audit, and
  licensing contracts.
- `cloud`: workspace, project, deployment, execution, storage, and gateway
  contracts.
- `marketplace`: catalog, publication, resolution, installation, verification,
  publishing, licensing, and enterprise-store contracts.
- `studio`: backend services, repositories, API contracts, workflow tooling,
  and the React client.

## Agent Runtime

The Agent Runtime provides explicit lifecycle, memory, tool-registry,
coordination, security, observability, and failure-handling boundaries.
Providers, tools, persistence, and network transports remain injected. Importing
the runtime does not start workers or connect to external services.

## Plugin Marketplace

Plugins use declared manifests, permissions, lifecycle hooks, signing, sandbox
contracts, and deterministic installation. Verification and trust decisions
remain separate from package resolution so operators can enforce policy before
activation.

## Enterprise Platform

Enterprise services model identity, organizations, tenant isolation, RBAC,
audit integrity and retention, and license entitlements. Reference in-memory
implementations are suitable for evaluation; production hosts must configure
durable storage, an identity provider, and enforcement at every entry point.

## Cloud Native

Docker Compose supports local and production-oriented topologies. Helm renders
Kubernetes workloads with probes, resource controls, autoscaling, disruption
budgets, RBAC, network policies, and optional observability resources. Values
must be reviewed for the target cluster and secret-management system.

## AI Studio

AI Studio supplies API, workflow, execution, project, chat, evaluation,
knowledge, prompt, and RAG surfaces. The frontend is built independently, and
the backend uses injected gateways and repositories. Studio does not create
provider credentials or hidden network clients at import time.

## Enterprise Marketplace

The Enterprise Marketplace adds organization-aware catalog, publisher,
licensing, entitlement, policy, audit, and approval contracts. Package signing
and verification remain mandatory trust boundaries; publication never implies
installation or execution.

## Deployment

Supported release assets are the Python wheel and source distribution, API and
Dashboard container definitions, Compose overlays, the Helm chart, Kubernetes
manifests, Nginx gateway configuration, migrations, and observability
configuration. Set all values from `.env.example` through the deployment
platform; never deploy the example values unchanged.

## Observability

The stack includes application health and metrics contracts plus Prometheus,
Grafana, Loki, Alloy, Alertmanager, PostgreSQL exporter, and Nginx exporter
configuration. Operators must configure retention, alert receivers, access
control, storage capacity, and redaction before production use.

## Security

No secrets are shipped in release artifacts. Runtime credentials are supplied
through the environment or a platform secret store. Server permissions use
explicit authentication and RBAC boundaries; plugins use declared permissions
and sandbox contracts; enterprise actions produce audit records. Containers
run with restricted filesystem and capability settings in the Helm defaults,
and network policy resources constrain ingress and egress. Production release
processes should pin and scan dependencies and images, generate an SBOM, sign
artifacts, verify provenance, and protect the publication environment.

## CI/CD

CI runs Ruff, the supported Python test matrix, package builds, Compose
validation, container builds, Kubernetes contract tests, Helm linting, and
default/production manifest rendering. Publication should consume only
artifacts produced from the protected `v3.0.0` tag after release approval.

## Upgrade Guide

1. Back up persistent databases, audit data, configuration, and signing keys.
2. Compare local configuration with `.env.example` and Helm values.
3. Install `tkai==3.0.0` with only the required extras.
4. Build the Dashboard and Studio clients from their lockfiles.
5. Render Compose or Helm configuration and inspect secrets, images, ingress,
   RBAC, network policies, storage, probes, and resource limits.
6. Apply database migrations through the bounded startup migration command.
7. Run health, API, Dashboard, Enterprise, Marketplace, and Studio smoke tests.
8. Retain the previous application image and database backup for rollback.

## Breaking Changes

The distribution version is unified at `3.0.0`; automation that expects the
older `1.3.0` package version must be updated. Helm chart and application
versions are now `3.0.0`, and frontend package metadata uses the same release
version. No intentional runtime API removal or new product behavior is included.

## Compatibility

Python 3.10 through 3.12 are the tested runtime targets. Existing Runtime 1.x
and SDK 2.x public contracts remain supported. FastAPI, PostgreSQL, Redis,
container, and frontend dependencies remain optional. Kubernetes requires
version 1.27 or later according to the chart metadata.

## Known Limitations

- Reference memory stores are not durable production persistence.
- Live PostgreSQL tests require an explicitly configured test database.
- External identity, secret management, TLS certificates, backup systems,
  artifact signing, and production registries are operator responsibilities.
- Compose is single-host and does not provide cluster high availability.
- Frontend bundles are built separately from the Python distribution.
- Cloud and enterprise packages provide contracts and reference services, not
  managed cloud control planes.

## Roadmap

Post-V3 work may improve durable adapters, identity-provider integrations,
policy enforcement, signed supply-chain automation, multi-cluster operations,
and end-to-end observability. These are roadmap directions, not V3.0 features
or commitments.

## Release Validation

The release gate is: Ruff, mypy, full pytest, deployment and release tests,
Dashboard and Studio builds, Docker/Compose configuration checks, Helm lint and
render checks, package build and artifact inspection, import/startup smoke
tests, and `git diff --check`. Environment-dependent checks must be recorded as
not executed rather than represented as passing.

## Tag Notes

`v3.0.0` prepares the unified TKAI Enterprise V3.0 release. It synchronizes
package, frontend, and Helm metadata; hardens packaging and documentation; and
contains no new product features.
