# TKAI Framework V1.3 RC-3 packaging and release validation

## Release checklist

- Baseline commit: `d7b571265df895f70947e2e911d1d14742596dc0`
- Candidate version: `1.3.0rc1`
- RC-1 integration validation: passed.
- RC-2 performance and reliability validation: passed.
- No tag, package publication, merge, or GA release was created.

## Packaging and distribution audit

The standard `build` module was unavailable in the local runtime. An offline
`pip wheel --no-deps --no-build-isolation` build produced
`tkai-1.3.0rc1-py3-none-any.whl`. The configured setuptools PEP 517 backend
also produced `tkai-1.3.0rc1.tar.gz` without downloading dependencies.

Both artifacts were audited for TKAI sources, the default template manifest and
README, project README, MIT license, build metadata, package version, Python
requirement, and the `tkai` command entry point. The audit rejected VCS data,
environment directories, Python/test/tool caches, `.env` files, and temporary
outputs. No credential or absolute-path content was found.

## Fresh-install validation

The wheel was installed into a temporary virtual environment using no network
access. Import/version, `tkai version show`, CLI help, legacy environment
Doctor, JSON AI Doctor, template-resource access, `BackendFactory`,
`TelemetryManager`, and `RuntimeScheduler` smoke checks passed. The temporary
wheel, sdist, build directory, and virtual environment are not committed.

## CLI and Doctor compatibility

The supported commands remain `tkai --help`, `tkai version show`, `tkai doctor`,
and `tkai ai doctor --json`. Root `tkai --version` and JSON output for the
legacy environment Doctor are not existing interfaces and were not added during
release validation.

## Quality gate

The complete test suite, Ruff, Black, Mypy, and `git diff --check` must pass
before this RC is handed to the release environment. Existing release tests are
run three times to detect order or state leakage.

## Known limitations

- Redis is optional and RC validation uses injected fake clients rather than a
  live Redis server, cluster, or cross-process deployment.
- Runtime scheduling remains explicit and does not take over `ProviderManager`.
- No active provider probing, traffic migration, automatic provider failover,
  or OpenTelemetry exporter is included.

## GA recommendation

RC-3 is suitable for final GA review after the release environment repeats the
artifact and quality-gate checks. Remaining manual steps are approval, branch
push, merge, annotated tag creation, and publication, each performed only when
explicitly authorized.
