# TKAI Framework V1.3.0 general availability preparation

## Release status

V1.3.0 is prepared for general availability on the release branch. This
preparation creates no Git tag, merge, GitHub release, or package publication.

- Baseline commit: `0f97f5607f6d81b8ce90f972df2dd13944911ad2`
- Version: `1.3.0`
- RC-1, RC-2, and RC-3 validation: passed.

## Feature summary

- Optional Redis distributed backend with lazy optional dependency loading and
  offline injected-client coverage; local memory remains the default.
- Explicit backend health probes, thresholded local-memory failover, and
  thread-safe local or optional Redis service discovery.
- Provider-neutral telemetry platform with local spans, metrics, structured
  logging, sampling, and exporter interfaces.
- Explicit adaptive runtime scheduler with deterministic policy decisions; it
  does not take over `ProviderManager`.

## Validation summary

- Benchmarks: offline Redis, health, failover, discovery, telemetry, scheduler,
  and combined-runtime scenarios use stable structural statistics only.
- Stress and reliability: bounded concurrency, lifecycle cleanup, injected
  Redis-failure recovery, exporter isolation, and scheduler no-candidate paths.
- Packaging: offline wheel and sdist audits validate package metadata, license,
  entry points, default template assets, and prohibited-content exclusions.
- Fresh install: a locally built wheel passed import, template, backend,
  telemetry, scheduler, CLI, and Doctor smoke checks in a temporary environment.

## Compatibility

V1.2 public imports, configuration precedence, and existing CLI commands are
preserved. `LocalMemoryBackend` remains the default; Redis, failover, discovery,
telemetry integration, and scheduling require explicit caller use.

## CLI and Doctor

Validated commands: `tkai --help`, `tkai version show`, `tkai doctor`, and
`tkai ai doctor --json`. The legacy environment Doctor remains text-only;
machine-readable AI diagnostics use the established `tkai ai` command.

## Known limitations

- Redis validation is limited to injected offline clients, not live clusters or
  cross-process deployments.
- No active provider probing, automatic provider failover, traffic migration,
  or OpenTelemetry SDK exporter is included.
- Runtime scheduling is explicit and does not replace `ProviderManager`.

## Upgrade notes

Upgrade from V1.2 by installing the V1.3.0 artifact in the normal release
workflow. Existing local-backend behavior requires no configuration changes;
Redis remains an optional dependency and explicit configuration choice.

## Rollback notes

Rollback by reinstalling the previous V1.2 artifact and retaining the default
local backend configuration. The new distributed facilities are additive and do
not require persisted schema or migration changes.

## Manual release steps

1. Push and merge the approved release branch.
2. Create annotated tag `v1.3.0` after approval.
3. Create the GitHub release and publish audited artifacts only when authorized.
