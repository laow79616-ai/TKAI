# V1.3 RC-1 integration baseline

## Scope

This release-candidate checkpoint validates the explicit V1.3 distributed and
runtime additions together with the existing Policy, Retry, EventBus, and
Telemetry foundations. It adds no runtime behavior and does not take ownership
of `ProviderManager`.

## Validation covered

- Offline `RedisBackend` construction with an injected fake client, active
  health probing, explicit failover evaluation, and service-registry selection.
- Explicit telemetry, coordinator, health-checker, failover, and registry
  lifecycle calls, including repeated stop operations.
- Scheduler selection and telemetry recording without provider or network I/O.
- Concurrent local backend, health-checker, and scheduler operations.
- Event subscriber failure isolation, Doctor JSON output, and AI CLI help
  smoke coverage.
- V1.2 public import-path and configuration precedence regression checks.

## Compatibility

All V1.3 facilities remain explicit and optional. `LocalMemoryBackend` remains
the default backend; failover, probing, discovery, telemetry integration, and
the runtime scheduler do not change the default provider execution path.

## Version audit

The repository's current package metadata and `tkai.__version__` still report
`1.2.0`. This RC-1 integration commit intentionally does not change release
versioning; V1.3 version preparation must update the single source of truth
before a V1.3 package release.

The established version CLI remains `tkai version show`; root `tkai --version`
is not currently an advertised command and is intentionally unchanged by this
compatibility-only validation.

## Known limitations

- Redis is optional and tested only through injected offline clients.
- There is no Redis high-availability cluster, cross-process service discovery,
  automatic provider failover, active provider probing, or traffic migration.
- The scheduler is an explicit local selection utility; it does not replace
  `ProviderManager` or dispatch provider requests.
